# 09 — V0.4R: Full learned RFL, end to end

$$\boxed{\text{Can the whole learned system actually learn better?}}$$

This version runs **only** if V0.1R, V0.2R and V0.3R have each passed their gates.
It is the first version in which a learned component is allowed to influence
learning, and it is deliberately last for that reason.

---

## 1. The chain, with every learned component marked

$$\text{Observed task failure} \to \text{Evidence} \to \underbrace{\hat p(C)}_{\text{V0.1R component}} \to \text{CandidateRepairs} \to \underbrace{\hat V(c)}_{\text{learned}} \to \text{SelectedRepair} \to \underbrace{\text{UnitSpecificUpdate}}_{\text{validated, V0.3R}} \to \text{Learning}$$

Each component has an upstream validation responsibility. Upstream closure must
cover the population actually used here: V0.1R's historical all-DGP result alone
does not establish failure-conditioned performance (`06-V01R.md` §1.1). The
version-specific and transfer gates must pass before this chain supports an
end-to-end claim.

### 1.1 Failure-only diagnostic boundary

The research mechanism diagnoses **why a task failed**, not why it succeeded.
All arms retain their declared ordinary task-learning rule. Successful episodes
receive task reinforcement and may be logged, but invoke no causal inference,
diagnostic query, repair-candidate scoring or extra diagnostic write. This applies
even to surprising or apparently lucky successes; high prediction error is not a
second trigger.

The outer orchestration reads only the **task-observed terminal result** supplied
by the environment: `SUCCESS` bypasses the diagnostic branch; `COLLISION`, `TRAP`
and `TIMEOUT` open that branch. These are the current kernel's native string
constants, not a new enum. The interface must establish that this terminal result
is task-observable; it may not expose evaluator cause labels, configured faults,
fired-mechanism truth or repair truth to decide whether to diagnose. A missing,
nonterminal or unrecognised result is a protocol error, never an implicit failure
and never permission to infer hidden causes.

This same boundary applies to `DirectFeedback`, `LearnedRFL` and `OracleRFL`.
Oracle information is available only inside its already-triggered failure
branch; it cannot override the trigger. `TraditionalRL` and
`NoDiagnosticCorrection` perform no diagnostic correction on either outcome.
Failure permits a bounded investigation, **not a mandatory edit**: keeping the
learner unchanged remains an admissible decision.

Before end-to-end collection, the runner must demonstrate zero diagnostic calls,
zero diagnostic query spend and zero diagnostic edits after success, while the
ordinary task update remains enabled. Failure cases must demonstrate the same
trigger rule across corrected arms, budget enforcement and a legal keep result.
Calling an offline inference instrument or a repair primitive directly in its
own test harness does not establish this orchestration guarantee.

Success-rate, recovery, retention and collateral measurements remain necessary
read-only outcome measurements. In particular, checking whether failure-driven
correction damages previously successful behaviour is knowledge protection, not
success-cause reflection. Saving a successful trace does not authorize a later
success-attribution objective or a new history-reinterpretation mechanism.

## 2. Arms

| arm | inference | repair selection | update |
|---|---|---|---|
| `TraditionalRL` | — | — | plain TD |
| `DirectFeedback` | feedback at face value | heuristic | V0.3R primitive |
| **`LearnedRFL`** | $\hat p(C)$ from V0.1R | $\hat V(c)$ learned | V0.3R primitive |
| `OracleRFL` | truth | truth | V0.3R primitive |
| `NoDiagnosticCorrection` | — | — | task TD only, no diagnostic edit |

`OracleRFL` is the ceiling **for this version**. If `OracleRFL` does not beat
`NoDiagnosticCorrection`, V0.4R is not interpretable and the failure belongs to
V0.3R, not here.

## 3. Candidate competition

Each candidate repair $c_i$ carries three quantities:

$$\hat V(c_i) \quad\text{(expected value if applied)}, \qquad U(c_i) \quad\text{(uncertainty)}, \qquad C_{\text{switch}}(c_i) \quad\text{(cost of changing course)}$$

$$\boxed{\mathrm{Score}(c_i) = \hat V(c_i) - \lambda\,U(c_i) - \beta\,C_{\text{switch}}(c_i)}$$

### 3.1 Doing nothing is a candidate

$$c_{\text{keep}} \in \mathcal C \quad\text{with}\quad C_{\text{switch}}(c_{\text{keep}}) = 0,\qquad \hat V(c_{\text{keep}}) = \text{the value of continuing}$$

This is the mechanism's most important property. It makes the following compete
on equal terms:

* change nothing;
* change one local decision;
* replace the strategy;
* repair the controller;
* acquire more evidence (spend counterfactual budget before deciding).

"It failed, therefore something must be edited" is not a rule the system is given.
It is a conclusion the system must be able to reach *or not reach*. The legacy
arms all edited unconditionally on failure, which is why `NoCorrection` kept
winning — an unconditional edit is a bad policy, and the experiments could not
tell that apart from "editing is bad".

### 3.2 The three coefficients

$\lambda$, $\beta$ are frozen before collection. A sweep over them is a secondary
contrast, and any reported result must state the values used. A system that wins
only at one $(\lambda,\beta)$ has not been shown to win.

$U(c_i)$ must be a genuine uncertainty — not a softmax temperature in disguise.
The legacy design briefs called for an independent (non-softmax) unknown channel
for exactly this reason, and the requirement carries over.

## 4. Endpoints

| endpoint | role |
|---|---|
| **RMST / DeficitAUC** vs `TraditionalRL` | **primary** |
| task success AUC | secondary (whole-curve; less suited than RMST — see `08` §3.5) |
| **CrossUnitCollateral** | co-primary |
| WithinUnitDamage | secondary |
| RepairPrecision | secondary |
| PolicyFlipRate | secondary |
| edit count, update mass | secondary |
| **CF queries spent** | always reported |

The primary claim is a conjunction, not a single number:

$$\boxed{\text{LearnedRFL recovers at least as fast as TraditionalRL \textbf{and} does so with lower collateral.}}$$

Stated as a conjunction because either half alone is trivially achievable —
recovering fast by doing nothing, or having zero collateral by never editing.

## 5. Failure localisation

This is what the four-version structure buys:

| observation | conclusion |
|---|---|
| `LearnedRFL` ≈ `OracleRFL` ≈ best | the learned pipeline works; the programme's claim is supported |
| `OracleRFL` good, `LearnedRFL` poor | the bottleneck is **inference or candidate selection** — return to V0.1R / V0.2R with a sharper question |
| `OracleRFL` ≈ `NoDiagnosticCorrection` | the bottleneck is the **primitive** — this is V0.3R's failure resurfacing, and V0.4R should not have been run |
| all arms ≈ `TraditionalRL` | the benchmark has no headroom; a **calibration** failure, not a scientific one |
| `NoDiagnosticCorrection` best | diagnostic editing is net-harmful in this environment — a clean and reportable negative |

Each row is a different, actionable outcome. Contrast this with the legacy
situation, where a single unfavourable AUC could have meant any of six things.

## 8. Not in this version

* neural attributors, DQN, GRPO, PPO, or any function approximation — the entire
  rebuild is tabular, CPU-only, single-process, so that every failure is
  interpretable;
* hierarchical options / SSP-BO / selective replay — these are *alternatives to*
  the primitive, to be tried only if V0.3R fails and redirects;
* human-feedback source weighting, CPO/CMDP — no version in the rebuild is
  indicated by the legacy evidence.
